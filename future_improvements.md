# Future Improvements

Concrete, actionable findings from a full read-through of the firmware, web UI, and build config. This is a planning/backlog document only — nothing here has been implemented. Items already known and explicitly deferred this session (altitude hold, true loiter circles, setup-mode diagnostics/test-outputs screens, differential-thrust mixing, SD card logging) are intentionally left out.

## Safety / failsafes

- **GPS "valid" flag still never gets cleared once a fix is lost (now mitigated).** `gps_task()`'s real-hardware loop (`main/gps.c:346`) only writes `latest_gps_data` `if (gps.valid)`, so a `$GPRMC` with status `V` is dropped and `latest_gps_data.valid` stays `true` at the last good fix. This is no longer dangerous: `gps_data_t` now carries `timestamp_us`, and every nav consumer (`get_fresh_fix()`/`get_current_heading_deg()` in `main/nav.c`) treats a fix older than `GPS_FIX_MAX_AGE_US` (2s) as no fix. Remaining cleanup: write `latest_gps_data.valid = false` on a status-`V` sentence so the flag means what it says, instead of relying on the age check alone.
- **No staleness/age tracking on IMU data.** GPS now has it (see above), but `imu_data_t` (`main/include/imu.h:92`) still has no timestamp: a run of failed `icm_read()` calls in `imu_task()` just logs "failed to read IMU" and leaves `imu_data` frozen, and `read_attitude()` (`main/main.c:702`) has no age check. Recommend a `last_update_us` field (mirroring `rc_input_t` and `gps_data_t`) and a max-age check in `read_attitude()` that forces the safe fallback once the attitude goes stale, not just when the IMU is outright absent.
- **RC signal-loss failsafe only watches one channel.** `get_rc_mode_status()` (`main/main.c:364`), which `control_task()` uses for signal loss, only tests `RC_SWITCH`'s own `last_update_us` via `is_stale()`, and `log_rc_gaps()` (`main/main.c:936`) only logs gaps on that same channel. If a different channel (aileron, elevator, throttle) loses its individual wire/signal while the switch channel keeps updating fine, staleness goes undetected and the frozen last-received value for that one channel gets passed straight through in manual mode. Consider checking staleness across all 6 RC channels, not just the mode switch.
- **RC capture's `last_update_us` updates even on a rejected pulse.** `rc_capture_cb()` (`main/rc_capture.c:31`) unconditionally refreshes `last_update_us` on every edge, even when the computed `width_us` fails the 800-2200us sanity check and gets discarded (`main/rc_capture.c:26-28`). A channel producing corrupted/glitchy edge timing (not a clean loss of signal) would never trip `is_stale()` even though `pulse_width_us` itself has been frozen at its last good value the whole time. Only refresh `last_update_us` when a pulse is actually accepted.
- **A transient IMU mutex timeout permanently disables autonomous mode for the rest of the boot.** `update_autonomous_outputs()` returns `false` both when `imu_ready` is false (a real, permanent driver failure — correct to latch) and when `xSemaphoreTake(imu_data_mutex, ...)` simply times out once (`read_attitude()`, `main/main.c:702-717`, `IMU_MUTEX_WAIT` = 15ms) — a transient contention blip, not a hardware fault. `control_task()` treats both identically and sets `critical_fault_latched = true` forever (`main/main.c:1083`), requiring a full power cycle to recover — which isn't possible mid-flight. Consider only latching on a sustained run of mutex-take failures (e.g. N consecutive), not a single miss.
- **Gyro bias calibration's timeout fallback is a silent no-op.** `calibrate_gyro_bias()` falls back to `GYRO_BIAS_*_DPS_DEFAULT` if the board never settles within `GYRO_CAL_TIMEOUT_MS` (`main/imu.c:236-240`), but those defaults are all hardcoded `0.0f` (`main/include/imu.h:85-87`) despite the comment there saying "placeholder until bench-derived from a real calibration run's logged result." In practice this fallback path currently means "apply zero correction at all" instead of the intended safety-net value. Run a real calibration, capture the logged `gyro_bias_x/y/z` output, and hardcode those numbers.
- **No mission waypoint coordinate validation.** `api_mission_post()` (`main/http_server.c:435`) checks that `lat`/`lon` are JSON numbers but never checks they're in a plausible range (`-90..90`/`-180..180`). A typo'd or malformed waypoint would be accepted and silently drive `heading_to_target()`/`distance_to_target()` (`main/gps_math.c`) with nonsense input, producing an unpredictable commanded heading/roll rather than a rejected request.

## Flight control / PID

- **`MADGWICK_BETA` (1.0, `main/imu.c:27`) is a first-attempt bench guess, not systematically tuned** — the in-code comment already says as much ("retune from real bench behavior... rather than assuming this value is final"). Unlike ROLL/PITCH/HEADING_PID_CFG, there's no SITL coverage for this at all (`sitl/`'s simulators inject attitude noise directly, they don't model raw accel/gyro/mag fusion) — worth a small offline harness that logs raw IMU samples during a bench disturbance and replays them through `MadgwickAHRS.cpp` at different beta values, rather than tuning by feel in the air.
- **Compass axis remap and hard-iron offsets are unverified against the real board.** `read_mag()`'s axis remap comment (`main/imu.c:164-167`) explicitly flags it as "NOT verified against this specific board," and `MAG_HARD_IRON_OFFSET_*_UT` (`main/include/imu.h:74-76`) are fixed constants bench-derived once, with a note to redo them "if the board's position relative to nearby servos/motor/wiring changes." Since these feed directly into `nav.c`'s heading-hold source, a wrong remap or stale offset could silently produce a consistently-wrong compass heading. Worth a simple in-field verification step (compare `imu-yaw` in the setup-mode UI against a known bearing) before ever trusting compass-based nav in flight, and ideally a documented recalibration step once the IMU is actually mounted in the airframe.

## Networking & web UI

- **Setup-mode AP password is a real value ("`flightline123`") committed and unchanged, despite its own comment saying to change it.** (`main/include/setup_mode_config.h:8-11`) The API is also completely unauthenticated once on the AP — anyone who's ever had the WPA2 password (or a fully open network, if it's ever blanked) can hit every `/api/*` endpoint with no session/token. Low real-world risk given the AP only exists in a deliberately-entered ground mode, but worth actually rotating the password before flying anywhere with other RF-capable people nearby, and treating the SSID/password as something to change per deployment rather than leave at the repo default.
- **No "connection lost" indicator in the web UI.** Every poll function (`pollOutputs`/`pollAirspeed`/`pollImu`/`pollGps` in `main/web/app.js:297-848`) silently swallows a failed fetch and just waits for the next interval. If the AP link actually drops while looking at, say, the live IMU or output-pulse-width readouts (exactly the screens used most heavily for bench verification this session), the numbers just freeze with no visual cue that they're stale rather than live. A simple "last updated Ns ago" or a banner after N consecutive poll failures would make bench sessions less error-prone.

## Hardware / unused features

- **`init_auxiliary_gpio()` and `aux_set_level()` are fully dead code.** Neither is called from anywhere in the firmware (confirmed via grep, 2026-10-08 — the only other reference to either is a comment in `main.c`). The README explicitly describes the AUX pins as being for "accessory things like LEDs, a payload-release servo/relay, etc." — the driver exists but nothing initializes the pins as outputs or exposes them through the setup-mode API. If any near-term plan depends on AUX outputs (payload release, status LED, buzzer), it needs `init_auxiliary_gpio()` called from `app_main()`/`setup_mode_run()` and likely a settable `/api/aux` endpoint, not just the existing driver.

## Testing / validation gaps

- **`AIRSPEED_PID_CFG` has no SITL coverage at all** (confirmed via `sitl/README.md` — it only covers `ROLL_PID_CFG`/`PITCH_PID_CFG` via `sitl_sim.exe` and `HEADING_PID_CFG` via `nav_sim.exe`). The current `k_p=2` is a desk estimate from the sensor's own accuracy spec (see the in-code derivation, `main/main.c:149-180`), not validated against an actual thrust/drag/mass plant model the way the attitude gains were. A throttle/airspeed plant model (thrust curve vs. RPM/PWM, drag vs. speed, mass) added to `sitl/` would let this gain get the same kind of systematic sweep-and-validate treatment the others already got.
